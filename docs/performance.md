# Performance

Generated by `beman.inside.bench` (tests/beman/inside/bench.test.cpp, ankerl::nanobench) — do not edit
by hand. Regenerate with `cmake --build <build-dir> --target beman.inside.perf_report`
(Release, `-O3 -DNDEBUG`, GCC 15, `-mfma` (BEMAN_INSIDE_FMA), no `-march`; one run pinned to a single
core with `taskset` on the maintainer's machine, `powersave` governor with
turbo — sub-ns rows move ±15–20% between runs, instruction counts don't).

Each table's FIRST row is the native implementation; the `relative`
column reads as native-time / row-time, so 100% is native parity and
smaller percentages are slower. Absolute ns/op values are host-specific
— the ratios are the stable signal. Instruction/cycle/branch columns
appear when the kernel grants perf-counter access.

Known slow paths (measured in the tables below, by design):
arithmetic with a rational-raw operand takes the exact rational path —
its cost is measured directly in the continuous-grid / rational-engine
tables against a hand-rolled reduced int64 fraction (the mixed
integer/notch-offset add and cross-grid non-integer stores have folded
integer fast paths, gated on imax-safe spans); a rational RHS in a
compound assign takes the same exact branch; `inside<checked>`
element-wise loops keep a per-element range check — prefer `beman::inside::sum`'s
bulk check, which validates the total instead.

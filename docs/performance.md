# Performance

Generated by `beman.inside.bench` (tests/beman/inside/bench.cpp, ankerl::nanobench) — do not edit
by hand. Regenerate with `cmake --build <build-dir> --target beman.inside.perf_report`
(Release, `-O3 -DNDEBUG`, GCC 15, `-mfma` (BEMAN_INSIDE_FMA), no `-march`; one run pinned to a single
core with `taskset` on the maintainer's machine, `powersave` governor with
turbo — sub-ns rows move ±15–20% between runs, instruction counts don't).

Each table's FIRST row is the native implementation; the `relative`
column reads as native-time / row-time, so 100% is native parity and
smaller percentages are slower. Absolute ns/op values are host-specific
— the ratios are the stable signal. Instruction/cycle/branch columns
appear when the kernel grants perf-counter access.

Known slow paths (measured in the tables below, by design):
arithmetic with a rational-raw operand takes the exact rational path —
its cost is measured directly in the exact-backed / rational-engine
tables against a hand-rolled reduced int64 fraction (the mixed
integer/notch-offset add and cross-grid non-integer stores have folded
integer fast paths, gated on imax-safe spans); a rational RHS in a
compound assign takes the same exact branch; `inside<checked>`
element-wise loops keep a per-element range check — prefer `beman::inside::sum`'s
bulk check, which validates the total instead.

## Comparison with `slim::optional` (1bb5fd9 → d07d272)

One-time snapshot of the switch from the sentinel-encoded `slim::optional`
to `std::expected<T, errc>` and full-range storage. Both commits were built
with identical flags and run as 5 interleaved rounds pinned to one core;
values are medians. Across all 202 rows present in both builds the median
after/before time ratio is 1.00 and 185 rows are within ±10%. Of the 17
outside that band, 16 have identical instruction counts before and after
(12 of them native/reference rows that share no library code) — timing noise
under the powersave governor; the remaining one is `clamp_cast` below. The
table lists the rows whose code path returns `std::expected` or whose
instruction count changed.

| Group / row | ns before | ns after | instr. before → after | Verdict |
|---|--:|--:|--:|---|
| div (u8) `a / b`, `div(a, b, snapped)` | 2.04 | 2.06 | 13 → 11 | unchanged |
| compound `/=` (u8) | 2.04 | 2.05 | 18 → 15 | unchanged |
| exact-backed div `inside<exact>` | 17.01 | 18.16 | 177 → 161 | noise (wide spread before, 13.0–17.5) |
| rational engine add | 8.32 | 8.17 | 177 → 183 | within noise |
| rational engine mul | 10.44 | 10.48 | 202 → 194 | within noise |
| exact-backed add `inside<exact>` | 6.36 | 6.86 | 134 → 146 | harness artifact¹ |
| casts `clamp_cast` | 0.75 | 1.52 | 18 → 39 | harness artifact¹ |
| mod (u8) `%`, `mod(a, b, snapped)` | 2.04 | 2.05 | 14 → 14, 11 → 11 | unchanged |
| transform v+1, `inside<{0,255}>` vs native | 1.92× native | 1.00× native | 7528 → 3775 | **faster** — now uint8 storage² |

¹ Standalone microbenchmarks of these exact kernels, built against both
commits, show identical instruction counts and timings (`clamp_cast` 18 instr. /
0.76 ns, exact add 143 instr. / 6.7 ns) and identical `clamp_cast` assembly;
the difference comes from how the large bench TU inlines neighbouring lambdas
after the sentinel group was removed.
² Without the reserved sentinel slot, `inside<{0,255}>` fits uint8 and runs at
native lane width; before it needed uint16 (the old workaround was
`inside<{0,254}>`). The `sentinel store` group no longer exists.

Takeaway: returning `std::expected` instead of the sentinel optional costs
nothing measurable on these paths — the wrapper only exists on the fallible
return and is consumed immediately.

Warning, results might be unstable:
* CPU frequency scaling enabled: CPU 0 between 800.0 and 4,900.0 MHz
* CPU governor is 'powersave' but should be 'performance'
* Turbo is enabled, CPU frequency will fluctuate

Recommendations
* Use 'pyperf system tune' before benchmarking. See https://github.com/psf/pyperf

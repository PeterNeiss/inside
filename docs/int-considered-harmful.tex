% ================================================================= title ====
\title{\vspace{-1.5cm}\textbf{int considered harmful}\\[0.4em]
       \large A case against the default integer, and a type that fixes it}
\author{Peter Neiss}
\date{18 October 2026}

\begin{document}
\maketitle
\thispagestyle{plain}

\begin{abstract}
\noindent
C++'s \code{int} is not a number. It is a platform-dependent bit pattern with
undefined behaviour at both ends of its range. It changes width and
signedness in the middle of expressions, it rounds without being asked, and it
records nothing about what it counts. C++26 changes none of this. This paper puts \code{int} in the dock
with eleven hazards, each a complete program with its real output. One of them
makes GCC emit \emph{no machine code at all} for \code{main}. The paper then
shows, more briefly, that reaching for \code{double} trades one kind of silent
wrongness for another.

It then presents \code{inside}, a header-only library (C++23 and later) in which the range
and step size of a number are part of its type. Arithmetic widens its result
type at compile time, so overflow is unreachable. Division by zero is a value
you can test. Fractions are exact rationals, physical units are checked
dimensions, and what happens at the edge of a range is a policy written in the
declaration. Performance has no single answer. Against code that gives the
same guarantee, \code{inside} is sometimes \emph{faster}, sometimes
byte-identical and sometimes substantially slower. We report all three,
together with the programs that produced them.
\end{abstract}

\section{The thesis}

Dijkstra's 1968 letter did not say that \code{goto} produced wrong answers. It
said that \code{goto} broke the link between the program on the page and the
process it described. The case against \code{int} is narrower, and in a sense
worse: \code{int} \emph{does} produce wrong answers. It produces them silently,
in code that compiles cleanly at maximum warning levels. It also produces them
by letting the compiler \emph{delete code the programmer wrote}, including the
check written to catch that very failure.

The root is a mismatch of models. The programmer thinks of \code{int} as
$\mathbb{Z}$. The standard defines it as a finite set with undefined behaviour
at the boundary, and lets the optimiser assume the boundary is never reached.
The two models agree where testing usually happens and disagree where it
usually does not. The information needed to check an operation is: what range
this value may occupy, what it counts, and what should happen if it leaves the
range. That information lives only in the programmer's head, or in a comment.

\code{inside} puts that information in the type, where the compiler can act on
it. The rest of this paper does four things:
\begin{itemize}
\item shows that the problem is real (\S\ref{sec:indictment}--\S\ref{sec:double});
\item shows that the usual defences do not solve it (\S\ref{sec:mitigations});
\item shows that a type-level answer does (\S\ref{sec:inside}--\S\ref{sec:correctness});
\item measures what that answer costs: sometimes nothing, sometimes a lot (\S\ref{sec:performance}).
\end{itemize}

% ============================================================================
\section{The indictment}\label{sec:indictment}

\subsection{Signed overflow is undefined, and the optimiser believes it}

Signed overflow does not wrap. It is undefined behaviour, so the compiler may
assume it never happens and optimise on that assumption. Take a function that
asks whether adding one to a number makes it bigger:

\lstinputlisting[firstline=12,lastline=16]{int-considered-harmful/h01_overflow_ub.cpp}

\noindent
\code{x + 1 > x} can be false only if \code{x + 1} overflows. Overflow is
undefined, so the compiler treats the comparison as always true and deletes it,
without a warning:

\begin{lstlisting}[style=term]
$ g++ -std=c++26 -O0 h01_overflow_ub.cpp -o h01 && objdump -d h01
0000000000001149 <grows(int)>:
    1149:   endbr64
    114d:   push   %rbp
    114e:   mov    %rsp,%rbp
    1151:   mov    %edi,-0x4(%rbp)     <- argument stored...
    1154:   mov    $0x1,%eax           <- ...and ignored. Return 1.
    1159:   pop    %rbp
    115a:   ret
\end{lstlisting}

\noindent
Note the flag: \textbf{\code{-O0}}. GCC folds the comparison during
translation, so a debug build does not protect you. No spelling of this check
survives, because the check itself is what gets deleted.

\begin{lstlisting}[style=term]
INT_MAX            = 2147483647
grows(INT_MAX)     = yes, always
INT_MAX + 1        = -2147483648
\end{lstlisting}

\noindent
The program reports that adding one always gives a larger value, and then
prints the smaller value it got.

\subsection{The same assumption deletes an entire function}

The assumption compounds. Here is a loop whose counter starts near the top of
the range:

\lstinputlisting[firstline=12,lastline=26]{int-considered-harmful/h02_overflow_loop.cpp}

\noindent
At \code{-O0} the counter wraps negative and the loop exits after three
iterations. At \code{-O2} the compiler follows the chain to its end:
\code{i > 0} cannot become false without overflow, so the loop is infinite, so
nothing after it is reachable, so \code{main} has no reachable exit:

\begin{lstlisting}[style=term]
$ g++ -std=c++26 -O2 -Wall h02_overflow_loop.cpp -o h02
$ objdump -d h02

0000000000001040 <main>:
    1040:   endbr64
    1044:   cs nopw 0x0(%rax,%rax,1)
    104e:   xchg   %ax,%ax

0000000000001050 <_start>:
\end{lstlisting}

\noindent
That is all of \code{main}: a landing pad and padding. There is no loop, no
\code{printf} and \textbf{no \code{ret}}. Execution falls through into
whatever comes next:

\begin{lstlisting}[style=term]
$ ./h02
Segmentation fault (core dumped)          [exit 139]

$ ./h02_compiled_at_O0
iterations = 3
\end{lstlisting}

\noindent
\code{-Wall} said nothing. The same source and the same compiler at two
optimisation levels give two results: one prints \code{3}, the other crashes
before running a single instruction of the program. Undefined behaviour is a
compile-time contract. Breaking it does not corrupt your result; it deletes
your program.

\subsection{Two's complement is asymmetric}

There are $2^{31}$ negative \code{int} values and only $2^{31}-1$ positive
ones. At one point in the range, negation and absolute value have no correct
answer.

\lstinputlisting[firstline=14,lastline=19]{int-considered-harmful/h03_intmin.cpp}
\begin{lstlisting}[style=term]
INT_MIN            = -2147483648
INT_MAX            = 2147483647
-INT_MIN           = -2147483648   <- still negative
abs(INT_MIN)       = -2147483648   <- still negative
\end{lstlisting}

\noindent
\code{std::abs} returns a negative number. That is not a library bug: there
is no correct value it could return.

\subsection{Division has two undefined inputs and no error value}

Integer division has no \code{NaN}, so its two invalid inputs have no result to
return. These are division by zero and \code{INT\_MIN / -1}, whose true answer
is \code{INT\_MAX + 1}. On x86-64 both raise \code{SIGFPE}:

\begin{lstlisting}[style=term]
$ ./h04_divzero 0
about to evaluate 10 / 0 ...
Floating point exception (core dumped)          [exit 136]

$ ./h04_divzero 1
about to evaluate -2147483648 / -1 ...
Floating point exception (core dumped)          [exit 136]
\end{lstlisting}

\noindent
The second case kills the process even though no zero is in sight. Code that
divides by a runtime value must check two special cases, and almost none does.

\subsection{Mixed signed/unsigned comparison}

When an \code{int} meets an \code{unsigned}, both become unsigned, and a
negative value becomes a huge positive one.

\lstinputlisting[firstline=13,lastline=24]{int-considered-harmful/h05_signed_unsigned.cpp}
\begin{lstlisting}[style=term]
-1 < 0u            = false
v.size()           = 0
v.size() - 1       = 18446744073709551615   <- not -1
loop body entered  = 4 times on an EMPTY vector
\end{lstlisting}

\noindent
\code{-Wall} warns about the literal \code{-1 < 0u}, but not about the loop,
where both sides are unsigned. Without the escape hatch, the loop over the empty vector would run about
$1.8\times10^{19}$ times and index past the allocation on its first pass. This
is a common source of exploitable memory-safety bugs, and it comes from a
\emph{comparison}.

\subsection{Small types do not stay small}

\lstinputlisting[firstline=12,lastline=28]{int-considered-harmful/h06_promotion.cpp}
\begin{lstlisting}[style=term]
uint8 * uint8 -> int? yes
200 * 200          = 40000
stored back in u8  = 64   <- truncated
char is signed?    yes (platform-dependent)
sizeof(int)        = 4 bytes here; the standard promises >= 2
\end{lstlisting}

\noindent
This output shows three portability hazards:
\begin{itemize}
\item The 8-bit product is computed in \code{int}, and the store truncates it.
\item Whether bare \code{char} is signed depends on the platform.
\item \code{int} is 2 bytes on plenty of shipping embedded hardware.
\end{itemize}

\subsection{Division truncates, and not in the direction you expect}

\lstinputlisting[firstline=10,lastline=17]{int-considered-harmful/h07_truncdiv.cpp}
\begin{lstlisting}[style=term]
 7 / 2             = 3   (exact answer 3.5)
-7 / 2             = -3   (rounds toward zero, not down)
 7 % 2             = 1
-7 % 2             = -1   <- negative remainder
mean(90,90,91)     = 90   (true mean 90.333...)
\end{lstlisting}

\noindent
Rounding toward zero is neither floor nor nearest. It is the only mode on
offer, it is applied silently, and it is wrong for averages, bill splitting and
percentages. Because the remainder is negative for negative operands,
\code{x \% n == k} fails as an index into a cyclic structure.

\subsection{Shifts}

\lstinputlisting[firstline=11,lastline=25]{int-considered-harmful/h08_shift.cpp}
\begin{lstlisting}[style=term]
1 << 31            = -2147483648   <- defined, and negative
-7 >> 1            = -4
-7 / 2             = -3   <- same "halve", other answer
1 << 32            = 1   <- undefined behaviour
\end{lstlisting}

\noindent
C++20 made signed shifts well-defined. \code{<<} now wraps modulo $2^N$, and
\code{>>} on a negative value rounds down. Defined does not mean right: a
positive value shifted into the sign bit silently turns negative, and halving
by \code{>>} and halving by \code{/} round in different directions. A shift
count that is negative, or not less than the width, is still undefined. x86
masks the count, so \code{1 << 32} printed \code{1} here. The standard
promises nothing, and only UBSan reported it.

\subsection{Narrowing is silent}

\lstinputlisting[firstline=11,lastline=24]{int-considered-harmful/h11_narrowing.cpp}
\begin{lstlisting}[style=term]
velocity (64-bit)  = 40000
stored as 16-bit   = -25536   <- sign flipped
int 300 -> char    = 44
\end{lstlisting}

\noindent
Since C++20 these conversions are defined: the value is reduced modulo $2^N$.
Defined is not the same as right, and nothing warns. This is Ariane 5 Flight 501 in miniature. In June 1996, a horizontal velocity
was converted to a 16-bit signed integer by software carried over from Ariane
4, where the value had been provably smaller. The conversion overflowed 37
seconds after ignition and the vehicle was lost. The code was correct for the
range it was written against, but nothing in the type recorded that range.

\subsection{The midpoint bug}

\lstinputlisting[firstline=9,lastline=20]{int-considered-harmful/h10_binsearch.cpp}
\begin{lstlisting}[style=term]
lo                 = 2147483644
hi                 = 2147483646
(lo + hi) / 2      = -3   <- outside [lo, hi]
lo + (hi - lo) / 2 = 2147483645   <- correct
\end{lstlisting}

\noindent
The midpoint of two in-range values lands outside the range. Bentley's
\emph{Programming Pearls} (1986) has this bug, and Bloch found it again in 2006
in the JDK's \code{Arrays.binarySearch}, where it had lived for nine years. The
problem is not a lack of care.

\subsection{The semantic hazard: \code{int} does not know what it counts}

Every hazard so far concerned range. This one concerns meaning, and no
sanitizer can catch it, because the arithmetic itself is valid.

\lstinputlisting[firstline=8,lastline=27]{int-considered-harmful/h09_units.cpp}
\begin{lstlisting}[style=term]
subtotal (cents)   = 3683
shipping (dollars) = 5
total              = 3688   <- charged 5 cents for shipping
compiles clean, runs clean, bills the customer wrong.
\end{lstlisting}

\noindent
Cents and dollars have the same type, so adding them is well-defined,
warning-free and wrong. The Mars Climate Orbiter was lost in 1999 to this class
of error: pound-force seconds where newton seconds were expected. No value was
out of range. What the number \emph{meant} was never written down anywhere the
compiler could see it.

\section{``Just use \code{double}''}\label{sec:double}

The usual answer to the above is floating point: a wider range, no trap on
division by zero, and fractions. \code{double} is the right tool for many
problems, but it does not fix these ones. It brings its own family of silent
wrongness. This section is shorter only because those failures are better
known.

\subsection{Decimal fractions are not representable}

\begin{lstlisting}[style=term]
0.1 + 0.2          = 0.30000000000000004441
0.3                = 0.29999999999999998890
0.1 + 0.2 == 0.3   ? false
\end{lstlisting}

\subsection{The error accumulates}

\lstinputlisting[firstline=7,lastline=16]{int-considered-harmful/d02_money_drift.cpp}
\begin{lstlisting}[style=term]
10000 x $0.01      = 100.00000000001425348728
expected           = 100.00000000000000000000
exactly $100.00    ? false
error              = 0.00000000001425348728
\end{lstlisting}

\noindent
After ten thousand transactions the ledger no longer balances to the cent. The
error is small enough to survive testing, and then it shows up in
reconciliation.

\subsection{Addition is not associative}

\lstinputlisting[firstline=8,lastline=17]{int-considered-harmful/d03_assoc.cpp}
\begin{lstlisting}[style=term]
(a + b) + c        = 1.0
a + (b + c)        = 0.0
equal              ? false
\end{lstlisting}

\noindent
The same three values give two answers depending on grouping. Change the
thread count of a parallel reduction, or let the optimiser re-associate a loop,
and the sum changes. Results are then not reproducible even from run to run.

\subsection{Integers stop counting at $2^{53}$}

\lstinputlisting[firstline=8,lastline=19]{int-considered-harmful/d04_precision.cpp}
\begin{lstlisting}[style=term]
2^53               = 9007199254740992.0
2^53 + 1           = 9007199254740992.0   <- unchanged
2^53 + 1 == 2^53   ? true
(1e16 + 1) - 1e16  = 0.0   (should be 1)
\end{lstlisting}

\noindent
Past $2^{53}$ a counter stops incrementing. That matters for identifiers and
timestamps that pass through JSON. The last line is catastrophic cancellation:
subtracting two nearly equal values wipes out every digit that mattered.

\subsection{\code{NaN} breaks equality and ordering}

\begin{lstlisting}[style=term]
0.0 / 0.0          = -nan
1.0 / 0.0          = inf   <- no error reported
nan == nan         ? false   <- breaks equality
nan < 1            ? false
nan > 1            ? false   <- neither; breaks sorting
nan + 1000         = -nan   <- contaminates the whole total
\end{lstlisting}

\noindent
An invalid operation does not trap. It yields a value that spreads silently
through every later computation. That value also breaks the strict weak
ordering \code{std::sort} requires, so sorting a range that contains a
\code{NaN} is undefined behaviour. Floating point is excellent for continuous
quantities over a huge dynamic range. It is a poor fit for money, counting,
identifiers and anything that must reproduce.

\section{Why the usual defences fall short}\label{sec:mitigations}

\paragraph{Sanitizers are runtime instruments.} UBSan detects overflow only
when it happens, and only in an instrumented build. It cannot see what the
optimiser already deleted. On our first example:

\begin{lstlisting}[style=term]
$ g++ -std=c++26 -O2 -fsanitize=undefined h01_overflow_ub.cpp && ./a.out
h01_overflow_ub.cpp:24:14: runtime error: signed integer overflow:
    2147483647 + 1 cannot be represented in type 'int'
INT_MAX            = 2147483647
grows(INT_MAX)     = yes, always
INT_MAX + 1        = -2147483648
\end{lstlisting}

\noindent
It reports line 24, the \code{printf} argument. It says nothing about
\code{grows()}, whose comparison was already folded away, so there was no
arithmetic left to instrument.

\paragraph{\code{-fwrapv} changes the language.} It removes the undefined
behaviour and makes the wrong answer reliable: the midpoint is still negative.
It fixes the UB, not the arithmetic.

\begin{sloppypar}
\paragraph{Contracts and hardening are runtime checks.} C++26 contracts
(\code{pre}, \code{post}, \code{contract\_assert}) put a precondition in the
declaration, and a hardened standard library traps an out-of-bounds
\code{v[i]}. Both check at runtime, only where someone wrote the predicate or
called the library. A contract's evaluation semantic may be \code{ignore}, and
then nothing is checked. Neither changes what \code{a + b} does.

\paragraph{The standard's helpers fix one call at a time.} \code{std::midpoint},
\code{std::cmp\_less} and \code{std::in\_range} (C++20) fix the midpoint and
the mixed comparison. C++26 adds saturation (\code{std::add\_sat},
\code{std::saturate\_cast}) and \code{<stdckdint.h>}, whose
\code{ckd\_add} reports overflow. Each works only at the call sites that
remember to use it, and only for the full range of a built-in type.
\end{sloppypar}

\paragraph{Static analysis is partial.} Range analysis across functions and
data structures is undecidable in general. No analyser can tell that one
\code{int} holds cents and another holds dollars, because nothing in the
program says so.

\paragraph{Safe-integer libraries solve one hazard.} \code{boost::safe\_numerics}
and \code{SafeInt} fix overflow (\S2.1--\S2.2). They do not handle units,
rounding policy or ranges narrower than the underlying type. They also check at
runtime what could have been rejected at compile time.

\medskip
\noindent
Every one of these tools works at a point where the necessary information has
already been thrown away: the range, the quantity, the rounding rule and the
behaviour at the boundary. The proposal is simply to record that information.

% ============================================================================
\section{\code{inside}: putting the range in the type}\label{sec:inside}

\code{inside} is a header-only library built around one template. It needs
C++23; C++26 adds grids past 64 bits and diagnostics that show values:

\begin{lstlisting}
template<grid G, policy_flag P>
struct inside;                        // include/beman/inside/core.hpp:98
\end{lstlisting}

\noindent
The \code{grid} is a compile-time value with two parts: an interval, and a
\emph{notch}, which is the step size held as an exact rational. Every value is
exactly $\text{Lower} + k \cdot \text{Notch}$ for some integer $k$. The
\code{policy} says what happens when a value would leave the range. The grid
alone determines the storage:
\begin{itemize}
\item the narrowest of \code{uint8}\ldots\code{int64} that can number every
      point;
\item an exact fraction for a continuous grid;
\item a wider integer for grids past 64 bits (\S\ref{sec:noceiling}).
\end{itemize}

\begin{lstlisting}
using namespace beman::inside;

using pct    = inside<{0, 100}>;                    // integers 0..100
using money  = inside<{{0, 1'000'000}, per<100>}, round_nearest>;  // cents
using angle  = inside<{0, 359}, wrap>;              // modular
using sample = inside<{{-1, 1}, per<16384>}, round_nearest>;       // Q1.14
\end{lstlisting}

\subsection{Arithmetic widens, so overflow is unreachable}

The result type of an operation is computed at compile time from the operand
grids. The sum of two values in $[10, 255]$ has the range $[20, 510]$, which no
input can overflow. There is no overflow to be undefined and nothing to check.

\lstinputlisting[firstline=13,lastline=33]{int-considered-harmful/b01_no_overflow.cpp}
\begin{lstlisting}[style=term]
a + b              = 236
a - b              = -204   (no wraparound)
(lo + hi) / 2      = 2147483645   (still in range)
\end{lstlisting}

\noindent
The listing shows three things:
\begin{itemize}
\item \code{static\_assert} verified the sum, so a wrong answer would fail the
      build, not a test.
\item The difference of two unsigned-ranged values has the grid
      $[-245, 245]$. It widened to a signed type instead of wrapping.
\item The midpoint from \S2.10 stayed in range, because \code{lo + hi} was
      computed in a grid wide enough to hold it.
\end{itemize}

\subsection{Division by zero is a value, not a signal}\label{sec:divzero}

Division returns a plain value when two things hold: the divisor's grid
excludes zero, and the exact quotient provably fits. The operand grids decide
both at compile time, and every integer grid satisfies the second. Otherwise
division returns \code{std::expected<inside, errc>}.

\lstinputlisting[firstline=14,lastline=36]{int-considered-harmful/b02_divzero.cpp}
\begin{lstlisting}[style=term]
7 / 3              = 7/3   (exact, not 2)
div(7, 3, trunc)   = 2
10 / 0             = division by zero   (no SIGFPE)
\end{lstlisting}

\noindent
By default the quotient is \emph{exact}: $7/3$, not $2$. Truncation is
available, but you ask for it by name. The divisor's grid $[0,100]$ contains
zero, so the result is an \code{expected}, and the failure that killed the
process in \S2.4 becomes a value you can test.

\subsection{Rounding is stated, not inherited}

\lstinputlisting[firstline=16,lastline=30]{int-considered-harmful/b07_rounding.cpp}
\begin{lstlisting}[style=term]
n / d              = -3.5   (exact)
rounded_nearest    = -4
rounded_floor      = -4
rounded_ceil       = -3
snapped (trunc)    = -3
\end{lstlisting}

\begin{sloppypar}
\noindent
\code{pos} excludes zero, so the exact quotient is a plain value. Each named
mode is honoured for negative operands, where truncation and flooring differ.
A property test pins $(a/b) \cdot b + a \bmod b = a$ across whole grids, in
every mode and with negative divisors
(\file{tests/beman/inside/div\_round.test.cpp:150}).
\end{sloppypar}

\subsection{The edge is a policy you declare}

Arithmetic never leaves its range. Only assignment into a narrower type can,
and what happens then is part of the declaration:

\lstinputlisting[firstline=18,lastline=46]{int-considered-harmful/b03_policies.cpp}
\begin{lstlisting}[style=term]
checked  200 ->    value does not fit its range
clamp    150 ->    100
wrap     370 ->    10
try_make  10 ->    value does not fit its range
with_clamp() 150 -> 100
\end{lstlisting}

\noindent
Wrapping is available, but here you request it, and it is well-defined. The
default is \code{checked}, and every policy checks unless it says
\code{unsafe}. For example, \code{round\_nearest} rounds first and then still
range-checks the result. To turn the check off, you have to write the word.

\subsection{Negation reflects the type}

Negating a $[\text{Lower},\text{Upper}]$ value gives a
$[-\text{Upper},-\text{Lower}]$ value, so the asymmetry of \S2.3 cannot arise:

\lstinputlisting[firstline=13,lastline=28]{int-considered-harmful/b10_negation.cpp}
\begin{lstlisting}[style=term]
coldest            = -40
-coldest           = 40   (representable by construction)
-hottest           = -125
\end{lstlisting}

\noindent
\code{-INT\_MIN} has no analogue, and for the same reason \code{abs} cannot
return a negative number.

\subsection{The scale is part of the type}

The notch records the scale, so a cent value and a dollar value have different
types, and combining them converts:

\lstinputlisting[firstline=14,lastline=33]{int-considered-harmful/b05_units.cpp}
\begin{lstlisting}[style=term]
subtotal           = $36.83
shipping           = $5
total              = $41.83   (not $36.88)
\end{lstlisting}

\noindent
A bare integer cannot enter the arithmetic at all, because nothing says which
grid it belongs to. The diagnostic says so:

\begin{lstlisting}[style=term]
$ g++ -std=c++26 -I ../../include x01_bare_int_rejected.cpp
   16 |   auto bad = x + 1;      // error: no grid for the literal
include/beman/inside/arithmetic.hpp:552:31: error: static assertion failed:
   an inside cannot be combined with a raw scalar: give the scalar a grid --
   `1_ins`, `just<1>`, or `inside<{lo,hi}>{n}` for a runtime value with a
   known range
\end{lstlisting}

\noindent
Scale is not the same as dimension. \file{units.hpp} builds quantities on
\code{inside}: units, dimensions, ISQ quantity kinds and quantity points
(\file{docs/units.md}). With them, the Mars Climate Orbiter mismatch converts
exactly, and adding an impulse to a length does not compile:

\lstinputlisting[firstline=15,lastline=33]{int-considered-harmful/b12_impulse.cpp}
\begin{lstlisting}[style=term]
100 N·s + 10 lbf·s = 144.4822161526050 N s
N·s + m            : does not compile
\end{lstlisting}

\noindent
A unit conversion only rescales the grid at compile time, so it is exact and
costs nothing at runtime. A call that does not compile states its reason:
\code{units: adding or comparing quantities of different dimensions}.

\subsection{Bounded indices}

\lstinputlisting[firstline=14,lastline=35]{int-considered-harmful/b08_index.cpp}
\begin{lstlisting}[style=term]
data[7]            = 49
index 10           = value does not fit its range   (no out-of-bounds access possible)
sum of all slots   = 285
\end{lstlisting}

\noindent
The bounds check runs once, at construction. An index that exists is in range,
and an index that would not be in range is never created.

\subsection{No 64-bit ceiling}\label{sec:noceiling}

Without static reflection, the limits and notch of a grid are 64-bit fractions.
With C++26 static reflection (GCC~16, \code{-freflection}) they have no size
limit:
\begin{itemize}
\item large grid numbers are interned in static storage
      (\code{std::define\_static\_array}), so equal grids are the same type
      however they are spelled;
\item the raw storage becomes a fixed-width integer sized from the grid.
\end{itemize}

\lstinputlisting[firstline=18,lastline=32]{int-considered-harmful/b11_no_ceiling.cpp}
\begin{lstlisting}[style=term]
$ g++-16 -std=c++26 -freflection -O2 -I ../../include b11_no_ceiling.cpp
a                  = 1000000000000000019884624838656
a * a              = 1000000000000000039769249677312000395398304974095154031886336
sizeof(a), sizeof(a * a) = 16, 32 bytes
1/3 on a 1e-30 grid = 0.333333333333333333333333333333
\end{lstlisting}

\noindent
The first line is not a typo. The literal \code{1e30} is a \code{double}, and
that is its exact value; an exact $10^{30}$ is spelled \code{1e30\_g}. The
product lives in $[0, 2^{200}]$, so the widening rule still applies: the result
is a plain 32-byte value, with no allocation. No \code{double} and no 64-bit
ratio can hold the notch $10^{-30}$. Compiled without reflection, the file is
rejected with a message naming the C++26 big-grid requirement.

\section{A worked migration}\label{sec:migration}

Here is an invoice in \code{int}. It has three defects, and the compiler
mentions none of them.

\lstinputlisting[firstline=11,lastline=23]{int-considered-harmful/m_before.cpp}
\begin{lstlisting}[style=term]
subtotal (cents)   = 268435456
tax  (8%)          = -21474836   <- overflowed
discount (1/3)     = 89478485   <- truncated
total              = 157482135

expected tax       = 21474836.48
expected discount  = 89478485.33
\end{lstlisting}

\noindent
On an invoice of \$2,684,354.56, \code{subtotal * 8} overflows and the tax
comes out negative. The discount loses its fraction, and the total is
meaningless. The same calculation in \code{inside}:

\lstinputlisting[firstline=15,lastline=45]{int-considered-harmful/m_after.cpp}
\begin{lstlisting}[style=term]
subtotal           = $2684354.56
tax  (8%)          = $214748.36   (exact, no overflow)
discount (1/3)     = $894784.85   (rounded to nearest cent)
total              = $2004318.07

discount on a 1/300 grid       = $67108864/75   (nothing was lost)
\end{lstlisting}

\begin{itemize}
\item \textbf{The overflow is gone by construction.} \code{subtotal * 0.08\_ins}
      widens to a grid that holds the product.
\item \textbf{The tax is exact to the cent.} \code{0.08\_ins} is an exact
      rational, not the nearest \code{double}. Storing into \code{money} rounds
      to nearest because the declaration says so.
\item \textbf{The third stays exact until it is stored.} On a grid of
      thirds of a cent it is exactly $67108864/75$ dollars. The rounding
      happened once, at storage, by a stated rule.
\item \textbf{The friction is small and deliberate.} Literals need a grid
      (\code{0.08\_ins}, \code{just<1, 3>}), and \code{money} needs a
      declaration. That declaration is where the range, scale and rounding rule
      get written down.
\end{itemize}

\section{Correctness}\label{sec:correctness}

\subsection{Errors caught before the program runs}

Grids are compile-time values and the arithmetic is \code{constexpr}, so whole
categories of defect become build failures:

\lstinputlisting[firstline=18,lastline=31]{int-considered-harmful/b06_compile_time.cpp}

\noindent
Every line is a \code{static\_assert}. An out-of-range constant is rejected
outright:

\begin{lstlisting}[style=term]
$ g++ -std=c++26 -I ../../include x02_range_rejected.cpp
error: 'constexpr void beman::inside::policy<W,E>::report(beman::inside::errc) const'
       called in a constant expression
error: call to non-'constexpr' function 'void beman::inside::detail::raise(beman::inside::errc,
       const char*)'
\end{lstlisting}

\noindent
The error path is deliberately not \code{constexpr}, so reaching it during
constant evaluation is a compile error. The library's
\file{tests/beman/inside/constexpr.test.cpp} relies on this: 159
\code{static\_assert}s that run inside the compiler.

\subsection{The error vocabulary}

How a failure is reported depends on how you spell the call, and the shape
matches the caller's role:

\begin{center}
\small
\begin{tabular}{@{}l >{\raggedright\arraybackslash}p{4.3cm} >{\raggedright\arraybackslash}p{6.4cm}@{}}
\toprule
Shape & Spelling & When \\
\midrule
Plain value & \code{a + b} & The type proves the operation cannot fail. \\
\code{expected<T,errc>} & \code{a / b}, \code{try\_make}, \code{to<T>()}, \code{math::tan} & It can fail at runtime. A math argument outside the domain for the whole input grid is a compile error instead. \\
Error code & \code{x.policy(ec) = v} & Hot paths; the first error sticks. \\
Throwing & default (\code{checked}) & Programming errors not handled locally. \\
Callback & \code{on\_clamp}, \code{on\_wrap} & The event is expected and carries data. \\
\bottomrule
\end{tabular}
\end{center}

\noindent
The codes form a small closed set (\file{detail/debug.hpp:30}). A value that
does not fit is always \code{overflow}, whichever path found it:

\begin{lstlisting}
enum class errc { domain_error, division_by_zero, overflow,
                  rounding_error, not_finite, invalid_format };
\end{lstlisting}

\noindent
There is no \code{<system\_error>} dependency. \code{set\_error\_handler}
replaces the failure path where exceptions are unavailable, which lets the
library run freestanding. Callbacks matter because some ``errors'' are the
domain's semantics. Seconds overflowing 59 is a carry:

\begin{lstlisting}
void add_seconds(auto n)
{
  seconds.on_wrap([&](auto, auto carry) { add_minutes(carry); }) += n;
}
\end{lstlisting}

\noindent
That is the whole carry logic of \file{examples/clock.cpp}.

\subsection{Exactness}

The notch is an exact rational, so cents and thirds have no approximation. Here
is the money example from \S\ref{sec:double}:

\lstinputlisting[firstline=15,lastline=30]{int-considered-harmful/b04_money.cpp}
\begin{lstlisting}[style=term]
10000 x $0.01      = $100.00
exactly $100.00    ? true
as a fraction      = 100/1
\end{lstlisting}

\noindent
The result is exactly one hundred dollars, in four bytes. The same computation
drifted by $1.4\times10^{-11}$ in \code{double}. Exactness needs no
arbitrary-precision arithmetic, because the grid is known at compile time and
the value is an integer count of notches. Nothing is stored as floating point.
A \code{double} enters through one exact rounding onto the grid and leaves
through one correctly rounded conversion.

\subsection{Reproducibility}

For integer and rational storage, \code{+ - * /} reproduce unconditionally,
because no floating point is involved. Conversion from \code{double} decodes
the IEEE-754 bits and needs no FPU.

\code{beman::inside::math} returns the \emph{correctly rounded} point of its
output grid, under the output's rounding mode. That result depends only on the
input and the grid, so it is the same at compile time, at runtime, and with or
without an FPU. Each result is computed with a proved error bound and escalated
(Ziv's strategy) until the bound puts it in one slot. Most calls are answered
by cheap tiers: compile-time tables for small grids, and the library's own
\code{double} and double-\code{double} kernels with proved bounds. An integer
path answers the rest, and it is the only path at compile time and without an
FPU. C++26 makes most of \code{<cmath>} \code{constexpr} but leaves its
accuracy unspecified, so a \code{std::sin} folded by the compiler need not
match the one computed at runtime. Against a long-double reference, every function's maximum error is 0.5000
notches (\file{docs/accuracy.md}). \code{-ffast-math} builds are refused with
an \code{\#error}. Correct rounding costs time, which
\S\ref{sec:mathcost} measures.

\section{Performance}\label{sec:performance}

The cost of \code{inside} is not a number. It is \textbf{a range with a
negative end}:

\begin{center}
\small
\begin{tabular}{@{}l >{\raggedright\arraybackslash}p{5.1cm} >{\raggedright\arraybackslash}p{5.9cm}@{}}
\toprule
Regime & When & Measured \\
\midrule
\textbf{Negative cost} & A chain of operations whose intermediate ranges the
grid arithmetic discharges; comparisons that run on raw storage. &
21\% faster than native checked (\S\ref{sec:checks}); scalar comparison at
130\% of native \\[0.6em]
\textbf{Zero cost} & Integer operands, where all the range reasoning happens in
the type system. &
Byte-identical disassembly (\S\ref{sec:codegen}); construct, add,
\code{std::accumulate}, sort, transform at 98--101\% \\[0.6em]
\textbf{Additional cost} & Continuous (rational) grids, element-wise checking,
transcendentals correctly rounded at full \code{double} resolution. &
rational add about 5$\times$ \code{double}; checked loop at 20\%; fine math
4--9$\times$ \code{std} \\
\bottomrule
\end{tabular}
\end{center}

\noindent
How the code is written decides the regime more than the library does. Code
that stays in \code{inside} lets the grids discharge obligations. Code that
round-trips through raw \code{int} at every step pays a check at each
boundary. Any summary of the form ``\code{inside} costs $N$\%'' is wrong in at
least one direction.

\subsection{The fast path is byte-identical to native}\label{sec:codegen}

\lstinputlisting[firstline=16,lastline=28]{int-considered-harmful/p01_codegen.cpp}
\begin{lstlisting}[style=term]
$ g++ -std=c++26 -O2 -I ../../include -c p01_codegen.cpp && objdump -d p01.o

0000000000000000 <inside_add(inside<...>, inside<...>)>:
   0:   endbr64
   4:   lea    (%rdi,%rsi,1),%eax
   7:   ret

0000000000000010 <native_add(int, int)>:
  10:   endbr64
  14:   lea    (%rdi,%rsi,1),%eax
  17:   ret
\end{lstlisting}

\noindent
The two are byte-identical, under the default \code{checked} policy: the sum
widens to $[0, 2000]$, so there is nothing to check. Loops still vectorise,
\code{inside} on 16-bit lanes (its storage for $[0,1000]$) and native on 32-bit
lanes. CI enforces this. \file{tests/beman/inside/check\_codegen.sh}
disassembles named kernels and fails on any \code{call} other than the cold
error report, and on a loop that does not vectorise.

\subsection{The like-for-like comparison}\label{sec:fair}

The fastest row in every table is plain, unchecked native code. It is fastest
because it does not do the job: it is the code of \S\ref{sec:indictment}.
The honest baselines are native code that enforces the same range, written as
a competent programmer would write it
(\file{tests/beman/inside/bench.test.cpp:62}):
\begin{itemize}
\item \code{native clamped}: \code{std::clamp(v, 0, 200)};
\item \code{native checked}: a hand-rolled bounded struct that throws on
      violation.
\end{itemize}
\file{p02\_fair\_bench.cpp} measures all five contenders on the same data: a
summed pass over 4096 values, repeated 20{,}000 times, with no throws.

\begin{center}
\small
\begin{tabular}{@{}l r r c r@{}}
\toprule
Implementation & ns/op & vs.\ unchecked & enforces? & vs.\ safe native \\
\midrule
\code{native unchecked}   & 0.439 & 100.0\% & no  & --- \\
\code{native clamped}     & 0.459 &  95.6\% & yes & 100.0\% \\
\code{native checked}     & 0.518 &  84.6\% & yes &  88.5\% \\

\end{tabular}
\end{center}

\noindent
\emph{Mean of three runs pinned to one core; GCC 15.2.0, \code{-std=c++26 -O2}, x86-64.}

The guarantee itself costs 5--15\% in plain C++. \code{inside<checked>} runs at
99.4\% of the hand-rolled checked struct, so the library adds under 1\% on top.
\code{inside<unsafe>} matches unchecked native. This is a favourable pattern:
a tight, predictable loop. It shows that the gap is small \emph{when you
compare against code doing the same work}, not that \code{inside} is free
everywhere.

\subsection{Where are the checks?}\label{sec:checks}

That benchmark gives \code{inside} nothing to prove. Every iteration converts
a raw \code{int} in and narrows the result back out, and that is the one shape
where a check cannot be avoided. Disassembling each step shows where checks
appear:

\begin{center}
\small
\begin{tabular}{@{}l l c@{}}
\toprule
Operation & Emitted & Check? \\
\midrule
\code{bchecked(int v)}            & \code{cmp \$0xc8,\%edi; ja ...} & yes \\
\code{auto c = a + b} (kept wide) & \code{movzbl; movzbl; lea; ret} & \textbf{none} \\
\code{bchecked c = a + b}         & \code{add; cmp \$0xc8,\%rax; jg ...} & yes \\
\code{checked\_u8 c = a + b} (native) & \code{add; cmp \$0xc8,\%eax; jg ...} & yes \\
\code{bchecked b = a} (same grid)  & \code{mov; ret} & \textbf{none} \\
\code{wide w = a} (widening)       & \code{movzbl; ret} & \textbf{none} \\
\bottomrule
\end{tabular}
\end{center}

\noindent
Checks appear in only two places: entering from a raw integer, and narrowing
into a smaller grid. The narrowing check is the same instructions as the native
struct's. A native checked type must re-validate after \emph{every} step of a
chain. \code{inside} lets intermediates widen and checks only the final store.
\file{p03\_check\_elision.cpp} sums four values in $[0,50]$ into $[0,200]$:

\begin{center}
\small
\begin{tabular}{@{}l r r c@{}}
\toprule
Implementation & ns/op & vs.\ unchecked & runtime checks \\
\midrule
\code{native unchecked}  & 0.874 & 100.0\% & 0 \\
\code{native checked}    & 1.067 &  81.9\% & 3 \\
\code{inside<checked>}   & 0.881 &  \textbf{99.2\%} & \textbf{0} \\
\bottomrule
\end{tabular}
\end{center}

\noindent
\code{inside<checked>} is \textbf{21\% faster than the native checked type}
and within noise of no checking at all. The sum provably fits $[0,200]$, so the
function is the same two \code{add}s and an \code{lea} as the unchecked
version. The native one has three \code{cmp}/\code{jg} pairs and spills. If the
result type is narrowed to $[0,199]$, the store check (\code{cmp \$0xc7,\%al;
ja}) reappears at once. Hand-written checks cannot be removed, because nothing
in \code{int} records what has already been established.

At full \code{double} resolution, correct rounding costs \textbf{4 to

\section{When not to use this}\label{sec:limits}

\begin{itemize}
\item \textbf{It is not yet ready for production.} Version 0.3 is at the Beman
      ``under development'' maturity level, and the API may change.
\item \textbf{It requires C++23}: GCC 14+, Clang 19+ (Clang 18 with libc++),
      or MSVC 19.51+. Grids past 64 bits need C++26 static reflection, which
      today means GCC~16 with \code{-freflection}.
\item \textbf{Compile times increase.} Arithmetic on grids is compile-time
      work, and it happens in your build.
\item \textbf{Error messages are template errors.} On the guided path a
      hand-written message names the fix (\S\ref{sec:inside}). Off it, you get
      the usual template output.
\item \textbf{Widening surprises \code{auto} users.} \code{a + b} does not
      have the type of \code{a}, so \code{auto} variables in a chain get
      progressively wider types. That is correct, but most C++ programmers do
      not expect it.
\item \textbf{Correct rounding is not free.} At \code{double} resolution it
      costs 4--9$\times$ \code{<cmath>}. Code that needs \code{double}
      throughput and tolerates \code{double} error should call \code{<cmath>}.
\item \textbf{Not everything needs it.} A loop counter is not where numeric
      bugs come from. The machinery pays off where a wrong answer is expensive:
      money, physical units, fixed-point signal processing, registers, control
      loops, and anything that crosses a system boundary.
\end{itemize}

% ============================================================================
\section{Conclusion}

The defects of \S\ref{sec:indictment} are not exotic. They are the arithmetic
of the type C++ programmers reach for by default, and carelessness does not
cause them. The midpoint bug lived nine years in the JDK, and Ariane 5 was
destroyed by code that had been correct on the previous rocket. These defects
persist because the information needed to catch them is absent from the
program:
\begin{itemize}
\item \code{int} does not know its range, so it cannot check it.
\item It does not know what it counts, so it cannot object to a mismatch.
\item It has no rounding policy, so it truncates.
\item It has no representation for failure, so division by zero kills the
      process.
\item Because overflow is undefined, the compiler may assume it never happens,
      and a program that should print \code{3} becomes a \code{main} with no
      instructions.
\end{itemize}

\code{inside} shows that a range, a step size and an edge policy written into
the type are enough to fix these. Overflow becomes unreachable, division by
zero becomes a value, rounding becomes a decision, and a unit mismatch becomes
a compile error. On the fast paths, it emits the same instructions as the
\code{int} it replaces.

For any number in your program, you already know its range, its units and what
should happen at its limits. Writing that down costs a line. Not writing it
down costs whatever the bug costs.
